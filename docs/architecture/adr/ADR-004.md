# ADR-004: PostgreSQL Enterprise Relational Engine & Hybrid JSON Modeling

- **Status**: Approved & Verified
- **Date**: July 28, 2026
- **Domain**: Persistent Database Storage Layer (`schema.prisma`)

---

## Context

The Neural Operating System (NOS) must reliably persist heterogeneous enterprise domain data spanning strictly structured relational hierarchies (organizations, departments, teams, users, device registration rosters, cryptographic API key hashes) and extensible, platform-variable operating system diagnostic snapshots (Windows Event logs, Linux `/proc` attributes, S.M.A.R.T. hardware disk health blobs, BitLocker encryption registries).

## Current Implementation Assessment

The existing system relies on **PostgreSQL 16** managed via the Prisma ORM query builder. An inspection of `apps/backend/prisma/schema.prisma` reveals 37 fully defined entity models utilizing standard 128-bit UUID primary keys, strict foreign key cascading relationships, and explicit `Json` datatype columns on extensible hardware discovery tables (`DeviceInventory`, `AuditLog`, `DeviceTimelineEvent`).

## Problem

Deploying purely NoSQL document databases (e.g., MongoDB) fails to guarantee multi-tenant referential integrity, making ACID transactional enforcement across organizational billing quotas and RBAC assignments complex and error-prone. Conversely, forcing rigid relational normalizations on constantly evolving operating system diagnostic outputs creates continual schema migration thrashing and table column bloat whenever an edge agent introduces a new hardware sensor field.

## Alternatives Considered

1. **Polyglot Persistence Split**: Using MySQL for relational enterprise multi-tenant account data while deploying an isolated MongoDB or Elasticsearch cluster strictly for raw diagnostic inventory logs and telemetry snapshots.
2. **Pure Fully Normalized Relational Schema**: Creating hundreds of micro-relational tables for every individual OS event log parameter and SMART drive attribute without permitting any binary JSON storage columns.

## Decision & Engineering Justification

We **solidify PostgreSQL as our single unified enterprise relational storage engine**, enforcing a **Hybrid Relational + Structured JSON modeling pattern**:

1. **Strict Relational Integrity for Domain Rules**: All core SaaS multi-tenant entities, user assignments, registration keys, and device identities utilize strict foreign keys with explicit cascading cleanup (`onDelete: Cascade` or `SetNull`).
2. **Structured JSON for Extensible Diagnostic Blobs**: OS-specific hardware discoveries (`eventLogs`, `windowsDefender`, `smartData`, `gpuInfo`) are persisted as validated PostgreSQL `JSONB`/`Json` storage types on parent inventory records (as currently verified in `schema.prisma` lines 228–240). This guarantees schema stability across OS evolution without requiring disruptive DDL database migrations for sensor upgrades.

## Consequences & Migration Impact

- **Positive Benefits**: Single unified enterprise database engine simplifies DevOps backup topology and failover; guarantees 100% ACID referential integrity; provides high-performance querying over indexed JSONB paths; pre-architected for seamless future declarative timestamp table partitioning on telemetry snapshots.
- **Negative Trade-offs**: Requires disciplined DTO schema validation in backend ingestion controllers (`Class-Validator`) before persisting dynamic JSON payloads to prevent garbage storage insertion.
- **Migration Impact**: **Zero**. Perfectly preserves our existing stable 37-table Prisma relational model without unapproved redesigns.
