# ADR-009: Multi-Tenant SaaS Isolation, Quota Enforcement & ABAC/RBAC Governance

- **Status**: Approved & Verified
- **Date**: July 28, 2026
- **Domain**: Tenant SaaS Isolation & Role Access Governance (`tenant`, `auth`, `users`)

---

## Context

As an enterprise SaaS platform, NOS hosts infrastructure monitoring data for independent organizations on a single shared physical application and database infrastructure. Guaranteeing complete data isolation across organizations is mandatory; under no circumstances can an operator in Organization A inspect, query, or mutate devices, telemetry, alert rules, or user profiles belonging to Organization B.

## Current Implementation Assessment

The existing system architecture centers around the top-level `Organization` table in `schema.prisma`. Every major primary domain entity (`Device`, `Alert`, `AlertRule`, `DeviceGroup`, `AuditLog`, `ApiKey`) directly or via cascading composition ties to an immutable `organizationId`. Furthermore, multi-tenant billing and SLA restrictions are tracked in real time via the linked `OrganizationQuota` entity model.

## Problem

In single-database multi-tenant SaaS deployments, missing a simple `.where({ organizationId })` clause in a single API route handler or repository query results in catastrophic cross-tenant data leakage and regulatory compliance violations. Additionally, permitting tenant users to enroll devices without hard computational boundaries risks noisy-neighbor resource starvation, where a single aggressive tenant exhausts database storage and telemetry pipeline processing for the entire platform.

## Alternatives Considered

1. **Database-Per-Tenant Isolation**: Provisioning a completely distinct, physically isolated PostgreSQL server database instance for every individual customer organization upon registration.
2. **Schema-Per-Tenant (PostgreSQL Schemas)**: Executing automatic DDL creation of an isolated database schema namespace (`CREATE SCHEMA tenant_4091`) within a shared PostgreSQL database instance per organization.
3. **Application-Level Soft Filtering Without Quotas**: Utilizing shared table rows filtered solely by application UI queries without enforcing backend database quota restrictions or strict role authorization guards.

## Decision & Engineering Justification

We **enforce a unified Shared-Schema Multi-Tenant Isolation Architecture protected by strict repository tenant bounding and automatic quota enforcement**:

1. **Universal Bounded Tenant Filtering**: Every read, write, update, and deletion query executing in `apps/backend/src/modules/*` repository layers must programmatically inject `.where({ organizationId })` derived from the validated JWT token session payload. Unbounded administrative global queries are constitutionally banned outside of dedicated super-admin verification routines.
2. **Real-Time Quota Interception**: Before processing resource onboarding mutations (e.g., enrolling new target devices via `POST /api/v1/device/register` or creating new API keys), application services inspect `OrganizationQuota` limits (`maxDevices`, `maxDailyTelemetry`). Breached limits instantly abort execution with HTTP `403 Forbidden (Quota Exceeded)`, eliminating noisy-neighbor starvation.
3. **Granular Role-Based (RBAC) & Attribute-Based (ABAC) Governance**: Access to sensitive administrative mutations is strictly mediated via NestJS guards implementing 10 canonical roles (`OWNER`, `ADMIN`, `OPERATOR`, etc.) paired with customizable tenant `PermissionProfile` conditions.

## Consequences & Migration Impact

- **Positive Benefits**: Maximizes database server resource consolidation and connection pool efficiency; ensures instantaneous tenant provisioning without running slow infrastructure provisioning scripts; guarantees compliance with data isolation guarantees; stops noisy-neighbor resource exhaustion.
- **Negative Trade-offs**: Demands extreme developer discipline and quality gate code verification (`QG-10`) to verify that repository queries never omit tenant ID scoping filters.
- **Migration Impact**: **Zero**. Confirms our verified multi-tenant OAT testing model (Checkpoint 7: "Enforces strict multi-tenant isolation across organizations") and preserves existing schema designs.
