# ADR-010: Enterprise Alert Notification Engine, Dead-Letter Queues & Resilience

- **Status**: Approved & Verified
- **Date**: July 28, 2026
- **Domain**: Incident Alerting & Omnichannel Notification Engine (`alerts`)

---

## Context
When an infrastructure hardware metric breaches an active alert threshold rule (`AlertRule`), system operators must be notified via external communication channels (Email, Slack webhooks, Discord, Teams, SMS, or third-party HTTP webhooks) to initiate immediate triage. Because third-party communication networks experience transient downtime, API rate limiting, and network latency, the alert evaluation engine cannot depend on external notification provider SLAs to complete real-time incident processing.

## Current Implementation Assessment
The existing system under `apps/backend/src/modules/alerts` coordinates alert evaluation and notification dispatching via decoupled interfaces (`INotificationProvider` in common layers, verified during Module 0 stabilization). The database model includes a dedicated `NotificationLog` table equipped with retry tracking (`retryCount`) and Dead-Letter Queue indicators (`isDlq: Boolean`).

## Problem
Executing synchronous external webhook HTTP POST calls directly within the primary real-time telemetry ingestion or rule evaluation loop causes network thread blocking. If a webhook target (such as an external Slack workspace or corporate SMTP server) hangs for 10 seconds or returns an error, synchronous blocking stalls backend API servers, exhausting database connections and delaying incoming telemetry heartbeats. Furthermore, if notification delivery attempts fail completely without logging or retry queues, critical infrastructure outage alerts disappear silently without notifying operational engineering teams.

## Alternatives Considered
1. **Synchronous Blocking Notification Dispatch**: Directly awaiting external email and Slack HTTP requests inside the primary `POST /api/v1/telemetry/snapshot` request lifecycle before returning HTTP 200 responses to edge monitoring agents.
2. **Fire-and-Forget Unlogged Broadcasting**: Executing background asynchronous promise calls (`provider.send().catch(() => {})`) without saving delivery records to database storage or attempting delivery retries after communication failures.
3. **External Enterprise Managed Notification Service**: Delegating all notification dispatching to specialized cloud platforms (e.g., PagerDuty or AWS SNS) while completely removing local notification logging capabilities.

## Decision & Engineering Justification
We **enforce an asynchronous, Decoupled Notification Architecture backed by database persistence and automatic Dead-Letter Queue (DLQ) retry workflows**:
1. **Asynchronous Decoupled Execution**: Upon incident generation in `AlertsService`, notification dispatch delegates to specialized provider singletons implementing `INotificationProvider` (`EmailNotificationProvider`, `SlackNotificationProvider`) outside the incoming telemetry execution path. Ingestion HTTP responses never await external third-party webhook completion.
2. **Persistent Audit Delivery Logging (`NotificationLog`)**: Every dispatch attempt records an immutable tracking entry in `notification_logs`, documenting provider channel, recipient address, network execution status (`SUCCESS` / `FAILURE`), and upstream server response payloads.
3. **Automatic Dead-Letter Queue (DLQ) Resiliency**: If an external provider rejects delivery or experiences connection timeouts, the log entry flags as `isDlq = true` and increments `retryCount`. A background asynchronous worker retries DLQ notification records via scheduled exponential backoff intervals (up to a maximum of 5 attempts over 24 hours) before triggering a terminal system alert for administrative review.

## Consequences & Migration Impact
- **Positive Benefits**: Complete isolation of real-time telemetry ingestion performance from external network latency; guarantees 100% notification auditability and retry resilience during outbound webhook outages; clean extensible interface (`INotificationProvider`) supports seamless addition of future enterprise communication channels.
- **Negative Trade-offs**: Retaining detailed log records of every outgoing notification pulse consumes additional database disk storage over time, necessitating automated pruning via scheduled retention cleanup tasks.
- **Migration Impact**: **Zero**. Confirms our verified Module 0 Operational Acceptance test assertions (Checkpoint 5: "Emits notifications across assigned channels when rules trigger") and preserves established schema implementations.
