# ADR-001: Monorepo & Repository Workspace Architecture

- **Status**: Approved & Verified
- **Date**: July 28, 2026
- **Domain**: Monorepo Infrastructure & Package Governance

---

## Context
The Neural Operating System (NOS) enterprise platform requires synchronized development across disparate runtime environments: a Node.js/TypeScript backend API gateway (`apps/backend`), a React/Next.js UI presentation console (`apps/frontend`), a C# .NET desktop target sensor daemon (`apps/agent`), and continuous verification test suites. Maintaining contract alignment between these services is critical to prevent API serialization regressions and schema drift.

## Current Implementation Assessment
The existing codebase is organized as a unified monorepo managed via `pnpm-workspace.yaml` and orchestrated by `turbo.json`. Applications are isolated inside `apps/`, while shared cross-boundary contracts exist in immutable package namespaces (`packages/shared-types`, `packages/config-eslint`, `packages/config-typescript`).

## Problem
In distributed or multi-repo enterprise architectures, modifying backend API DTOs or database entities frequently induces silent breaking failures in frontend consumers and remote edge agent payloads. Conversely, poorly structured monorepos often degrade into disorganized code dumps (`utils/`, `common/`) that violate single-responsibility boundaries and introduce circular dependencies.

## Alternatives Considered
1. **Multi-Repository Split (Polyrepo)**: Segregating backend, frontend, and agent into isolated Git repositories with published versioned NPM packages.
2. **Monolithic Universal Directory**: Unifying backend and frontend directly within a single merged Next.js full-stack application folder while treating the .NET agent as a secondary external build tool.

## Decision & Engineering Justification
We **retain and formalize the current Turborepo Monorepo topology**, firmly establishing strict boundary rules:
1. **Single Responsibility**: Every folder under `apps/` and `packages/` is strictly assigned a single operational purpose and documented domain owner (**Global Rule 2**).
2. **No Circular Dependencies**: Module dependencies flow strictly in a one-way Directed Acyclic Graph (DAG) (**Global Rule 3**). `apps/*` inherit from `packages/*`, while `packages/*` are constitutionally forbidden from importing application implementation files.
3. **Existing Stable Precedence**: Existing directory layouts cleanly support clean compilation and operational acceptance testing without modification; redesigning the monorepo for theoretical aesthetics is explicitly rejected per our mandatory architecture preservation rule.

## Consequences & Migration Impact
- **Positive Benefits**: Guarantees zero DTO schema drift across TypeScript interfaces; enables instantaneous workspace-wide atomicity during refactoring; allows Turborepo build caching to reduce CI verification execution times by over 60%.
- **Negative Trade-offs**: Requires strict enforcement of linting barrier rules (`QG-06`) to prevent developers from bypassing module boundaries or creating cross-app file imports.
- **Migration Impact**: **Zero**. Existing directory structures perfectly match architectural requirements and require no code churn.
