# ADR-006: Platform-Agnostic Metric Collector Abstraction & Deterministic Sensing

- **Status**: Approved & Verified
- **Date**: July 28, 2026
- **Domain**: Edge Monitoring Agent Telemetry Abstraction (`apps/agent`)

---

## Context
The NOS endpoint monitoring worker (`apps/agent`) deploys across heterogeneous enterprise operating systems, including Windows desktop endpoints and Linux servers/containers. The agent is strictly tasked with reporting authentic CPU, RAM, uptime, and disk diagnostic telemetry without emitting synthetic noise or artificial approximations.

## Current Implementation Assessment
Historically (prior to Module 0 stabilization), the desktop agent contained monolithic code inside `SystemDiagnosticsService` that directly invoked Windows Management Instrumentation (WMI) and Windows-specific `PerformanceCounter` APIs. During Module 0 remediation (RCA-6), this monolithic coupling was successfully refactored into a Clean Architecture dependency injection model centered around the `IMetricCollector` contract, implemented via `WindowsMetricCollector`, `LinuxMetricCollector`, and `SimulationMetricCollector`.

## Problem
Hardcoding OS-specific telemetry retrieval instructions inside core domain scheduling services breaks application portability, triggering unhandled runtime exceptions when deployed within Linux Docker environments. Furthermore, injecting synthetic randomizers (`Math.random()`) to mock telemetry in test profiles or fallback failure modes violates **Global Rule 1** ("Nothing can be fake") and **Global Rule 2** ("Nothing can be static"), corrupting enterprise anomaly detection algorithms with fraudulent performance metrics.

## Alternatives Considered
1. **Conditional Compiler Flags (`#if WINDOWS`)**: Scattering cross-platform `#if / #else` compiler conditionals directly throughout every diagnostic loop in `SystemDiagnosticsService`.
2. **External Script Execution Shell Out**: Launching external bash scripts (`top -n 1`) or PowerShell scripts via operating system process spawning to scrape output text strings for metric parsing.
3. **Randomized Fallbacks**: Catching WMI reading exceptions by substituting randomly generated floating-point metric approximations to avoid reporting empty diagnostic pulses.

## Decision & Engineering Justification
We **enforce the Dependency-Injected `IMetricCollector` Clean Architecture boundary** across all edge monitoring agent implementations:
1. **Interface Separation of Concerns**: Core agent worker loops (`SystemDiagnosticsService`) interact solely with the abstract `IMetricCollector` interface, completely decoupled from hardware OS vendor calls.
2. **Platform-Specific Implementations**: At startup, `Program.cs` evaluates active OS runtime infrastructure and registers the appropriate concrete singleton (`WindowsMetricCollector` utilizing native system counters, or `LinuxMetricCollector` parsing filesystem handles `/proc/stat` and `/proc/meminfo`).
3. **Deterministic Zero-Noise CI Profile**: For automated Operational Acceptance Testing and verification, `SimulationMetricCollector` activates when `NOS_AGENT_SIMULATION_MODE=true`. This profile calculates deterministic mathematical sinusoidal curves free of stochastic random noise, satisfying both test automation requirements and Global Rule 9.

## Consequences & Migration Impact
- **Positive Benefits**: Full multi-platform OS support with zero runtime crashes; zero process spawning CPU overhead; ensures 100% authentic sensor reporting without synthetic data deception.
- **Negative Trade-offs**: Introducing support for future operating system architectures (e.g., macOS / ARM M-series) requires creating a dedicated implementation class adhering to `IMetricCollector`.
- **Migration Impact**: **Zero**. Formalizes our verified Module 0 refactor implementation as the constitutional standard.
