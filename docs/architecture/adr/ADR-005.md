# ADR-005: JWT Stateless Authentication & Salted Secret Hashing

- **Status**: Approved & Verified
- **Date**: July 28, 2026
- **Domain**: Cryptographic Identity Security & Session Lifecycle (`auth`, `users`)

---

## Context
In a multi-tenant infrastructure operations platform, secure authentication is paramount. System operators, administrative APIs, and thousands of distributed edge agents must cryptographically verify their identity across every HTTP request and WebSocket handshake without exposing plaintext secrets or inducing massive latency bottlenecks at the authentication gateway.

## Current Implementation Assessment
The existing authentication infrastructure located under `apps/backend/src/modules/auth` and modeled in `schema.prisma` implements role-based access control via JWT issuance, supporting 10 canonical roles (`Role` enum). Database entity definitions explicitly mandate cryptographic token storage via dedicated hash fields (`refresh_tokens.tokenHash`, `api_keys.tokenHash`, `devices.tokenHash`, `user_sessions.tokenHash`).

## Problem
Session-cookie based architectures require persistent state lookups across distributed API servers, complicating load balancing and introducing Cross-Site Request Forgery (CSRF) vulnerabilities. However, issuing non-expiring or long-lived static JWT access tokens makes instantaneous operator account revocation impossible during suspected compromised security events. Furthermore, persisting unhashed refresh tokens or API secrets in database tables exposes entire customer infrastructure fleets to immediate account takeover if read-only database backup theft occurs.

## Alternatives Considered
1. **Stateful Server Session Cookies**: Storing session data directly in server application memory or querying Redis for session validity on every incoming HTTP API request.
2. **Plaintext Secret Storage**: Persisting raw API keys and refresh tokens in PostgreSQL tables to simplify simple equality lookup syntax during login challenges.

## Decision & Engineering Justification
We **enforce a stateless short-lived JWT architecture paired with strict constant-time cryptographic secret hashing**:
1. **Short-Lived Stateless Access JWTs**: Operator access tokens are cryptographically signed using HMAC-SHA256 (or asymmetric RSA public/private key pairs in production) with a strictly bounded expiration timeframe of **15 minutes**. API controllers authenticate tokens statelessly in memory via signature verification without querying database storage.
2. **Salted Hash Secret Persistence**: Long-lived refresh tokens, API keys, and device ingestion tokens are **constitutionally banned from plain-text persistence**. The database stores strictly salted cryptographic hashes (`tokenHash`). During authentication handshakes, incoming tokens are hashed in-memory and compared using constant-time verification algorithms to defeat timing side-channel attacks.
3. **Instant Session Revocation**: Compromised operator accounts or revoked API keys assert an immediate `isRevoked = true` state change on `user_sessions` and `api_keys` records, instantly blocking refresh token exchanges and real-time WebSocket connection upgrades.

## Consequences & Migration Impact
- **Positive Benefits**: Completely immune to database backup data theft; zero database read latency overhead on normal high-frequency API ingestion routes; native defense against CSRF attacks via custom `Authorization: Bearer` header requirements.
- **Negative Trade-offs**: Revoking an active access token before its 15-minute natural TTL expiry requires short-duration blacklisting in Redis cache layers during hyper-sensitive administrative lockouts.
- **Migration Impact**: **Zero**. Re-affirms existing stable schema hash constraints (`tokenHash`) and auth module guard implementations.
