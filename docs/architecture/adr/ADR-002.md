# ADR-002: Layered Clean Architecture & Dependency Inversion

- **Status**: Approved & Verified
- **Date**: July 28, 2026
- **Domain**: Backend Application Core (`apps/backend`)

---

## Context
As an enterprise SaaS platform monitoring thousands of distributed infrastructure nodes, the backend application (`apps/backend`) processes high-frequency telemetry, evaluates real-time alert syntax rules, manages multi-tenant user authentication, and coordinates asset inventory diffing. To support scalable feature development without introducing breaking regressions, business logic must be isolated from infrastructure transport implementations.

## Current Implementation Assessment
The existing NestJS application within `apps/backend/src` organizes domain features into distinct bounded context modules (`alerts`, `auth`, `device`, `fleet`, `inventory`, `realtime`, `telemetry`, `tenant`, `users`). Each module maintains separate controller, service, and DTO definitions, with centralized database access managed via `PrismaService` in the `common/` layer.

## Problem
In highly coupled web backends, business logic frequently leaks directly into HTTP controller methods or database model callbacks. Such spaghetti coupling prevents unit testing in offline isolation, makes schema evolution hazardous, and forces developers to construct fragile mock databases just to verify algorithmic calculations (such as alert threshold simulations).

## Alternatives Considered
1. **Monolithic Fat-Controller Pattern**: Embedding SQL query builders, authentication evaluation, and business calculation directly inside route controller methods for expedited initial development speed.
2. **Hexagonal Architecture (Ports & Adapters)**: Designing complete mathematical adapter interfaces for every internal library call, including logging and local utility math functions.

## Decision & Engineering Justification
We **adopt and enforce a strict Five-Tier Layered Clean Architecture** across all backend domain modules:
1. **Controller Layer**: Handles raw HTTP/WebSocket transport, DTO parsing, and guard authentication.
2. **Application Layer**: Contains core business orchestration logic and cross-module workflow execution.
3. **Domain Layer**: Houses pure enterprise entities, enums, and abstract TypeScript repository contracts from `@nos/shared-types`.
4. **Repository Layer**: Encapsulates Prisma ORM queries while strictly forcing multi-tenant `.where({ organizationId })` filters.
5. **Infrastructure Layer**: Manages low-level database and Redis network pooling.

*Justification*: By enforcing strict downward-only dependency boundaries, application business logic remains 100% testable in offline memory isolation without booting database sockets, directly enabling our verified 31/31 passing Operational Acceptance Test suite.

## Consequences & Migration Impact
- **Positive Benefits**: Complete separation of concerns; seamless offline unit testing; ensures database schema migrations never force rewrite of core business validation rules.
- **Negative Trade-offs**: Increases boilerplate file creation per feature module (requiring separate controller, service, repository interface, and module registration files).
- **Migration Impact**: **Zero structural churn**. Existing domain modules (`alerts`, `device`, `inventory`) already follow this clean dependency separation and are formalized as the immutable standard.
