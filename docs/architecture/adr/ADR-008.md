# ADR-008: Secure Zero-Touch Agent Registration Flow & Opaque Token Handshake

- **Status**: Approved & Verified
- **Date**: July 28, 2026
- **Domain**: Device Enrollment & Fleet Authentication (`fleet`, `device`)

---

## Context

Deploying monitoring agents across enterprise infrastructure requires an onboarding workflow that supports automated deployment (via MDM, SCCM, or Ansible scripts) without exposing sensitive database administrative user passwords or global API credentials to remote end-user workstations.

## Current Implementation Assessment

The existing registration architecture implemented across `apps/backend/src/modules/fleet` and `apps/backend/src/modules/device` utilizes Registration Keys (`RegistrationKey` model in `schema.prisma`). Target nodes invoke `POST /api/v1/device/register` supplying an enrollment key header (`X-Registration-Key` or payload parameter). Upon successful validation against `registration_keys.keyHash`, the backend creates or maps the `Device` record, generating an unique hardware UUID and an opaque cryptographic ingestion token (`tokenHash`).

## Problem

Embedding persistent enterprise operator username/password combinations directly inside deployment installation scripts creates major security vulnerabilities. Alternatively, accepting unauthenticated anonymous node self-registration exposes the system to unauthorized third-party device spam, denial of service attacks, and multi-tenant quota exhaustion. Furthermore, schema mismatches between testing enrollment parameters (such as explicit test multi-tenant binding via `organizationId`) and production DTO boundaries cause compilation build breakage during continuous integration verification.

## Alternatives Considered

1. **Operator Interactive Login on Endpoint**: Requiring a human systems operator to physically open a web browser on every individual target machine during initial setup to input JWT admin credentials.
2. **Mutual TLS (mTLS) Client Certificate Issuance**: Engineering an active public key infrastructure (PKI) Certificate Authority (CA) inside the backend to cryptographically sign X.509 client certificates for every agent workstation.
3. **Static Pre-Assigned Node Tokens**: Manually generating database records and individual token keys for every node in the web dashboard prior to executing physical agent installers.

## Decision & Engineering Justification

We **adopt and enforce the cryptographic Registration Key zero-touch enrollment architecture**:

1. **Pre-Shared Fleet Enrollment Secrets**: Administrators generate scoped, usage-limited `RegistrationKey` entities within the web console. Deployment scripts inject this key during automated agent installation.
2. **Salted Hash Secret Validation & Opaque Token Issuance**: Incoming registration requests validate the key hash, verify tenant maximum quota limitations (`organization_quotas.maxDevices`), and issue an opaque, cryptographic, revocable device ingestion token (`tokenHash`). Edge agents store solely this unique device token; the original enrollment registration key is discarded from memory after initial setup completes.
3. **Harmonized Test Interface Compatibility**: In strict alignment with our verified Module 0 repair (RCA-5), optional `organizationId?: string` mapping is natively supported in `RegisterDeviceDto` contracts to allow deterministic Operational Acceptance Testing across multi-tenant boundaries without breaking strict production isolation rules.

## Consequences & Migration Impact

- **Positive Benefits**: Facilitates rapid automated bulk enrollment across thousands of enterprise workstations; isolates device authentication to revocable, individual per-device cryptographic token hashes; prevents unauthorized third-party spam onboarding.
- **Negative Trade-offs**: If an active unexpired `RegistrationKey` secret is accidentally leaked to an untrusted network, unauthorized machines could self-enroll until the tenant administrator invokes key revocation (`status = 'REVOKED'`).
- **Migration Impact**: **Zero**. Fully preserves verified registration controller logic, shared DTO definitions, and Operational Acceptance verification models.
